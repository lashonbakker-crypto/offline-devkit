# 从小工具里学习工程判断

这个项目的目的，是让工具可用，也让实现可以读懂。先看 [命令手册](usage.md) 跑一遍，再从下面三个入口读源码。

## JSON：验证与保留数字分开做

入口：[json_tools.py](../offline_devkit/json_tools.py)。

1. `json.loads` 负责语法验证，不自己编写 JSON 语法解析器。
2. `parse_int` 和 `parse_float` 接收原始数字字符序列，把它保存为 `_Number`。
3. `object_pairs_hook` 接收每层对象的键值对，在转换成字典前检查重复键。
4. `parse_constant` 拒绝 Python 默认允许的 `NaN`、`Infinity`。
5. 渲染时先判断 `_Number`，直接写出合法数字；普通字符串则调用 `json.dumps` 做转义。

关键顺序：`_Number` 继承 `str`，因此必须先处理 `_Number`，再处理普通字符串。否则数字会被错误写成带引号的字符串。

不要把 `parse_json` 的结果当作普通算术数据使用。数字保留为私有字符串类型，是为了格式化；如果要计算，应在业务层明确采用 `decimal.Decimal`、整数或浮点数。

字符串转义可以改变，而数字原文不变。[技术笔记 01](01-json-numbers.md)提供可复现例子。

## 重复文件：每个筛选条件都有职责

入口：[files.py](../offline_devkit/files.py)。

| 阶段 | 做什么 | 为什么 |
| --- | --- | --- |
| 目录扫描 | 收集路径、长度、mtime、设备、inode | 跳过链接、依赖目录和特殊文件 |
| 硬链接去重 | 同一设备与 inode 只参与一次 | 多个路径可能本来就是同一个文件 |
| 大小分组 | 同长度才进入哈希候选 | 不同长度的内容不可能相同 |
| 分块哈希 | 每次读取最多 1 MiB，更新 SHA-256 | 大文件不会整体占用内存 |
| 前后核对 | 检查元数据与实际读取长度 | 检出可观察的修改和替换 |
| 报告整理 | 明确列出分组和读取错误 | 不把处理失败伪装成“没有重复” |

哈希一致是工程上的重复判断依据，不是数学上的无碰撞证明。字节级比较、稳定快照、目录句柄的竞态防护都是后续独立任务，当前没有实现。

扫描需要保存 O(n) 条文件元数据，哈希读取的时间与候选文件的总字节数相关。只有长度重复的文件参与哈希，所以 `files_hashed` 往往小于 `files_scanned`。整理与排序也有相应时间成本。

元数据通过 `Path.lstat()` 获取，避免 Windows 的 `DirEntry.stat()` 把设备与 inode 返回为零，导致正常文件被误判为发生变化、硬链接无法去重。这里多取一次完整元数据，是为了与后续 `fstat()` 使用同一套文件身份信息。详见 [Python 官方说明](https://docs.python.org/3.12/library/os.html#os.DirEntry.stat)。

## CLI：结果与退出码都属于接口

入口：[cli.py](../offline_devkit/cli.py)。

`argparse` 验证参数。核心模块产生数据，CLI 决定展示为人类可读文本还是 JSON。错误数组非空时返回 2；`dupes --fail-if-found` 才把“发现重复”映射为 1。这样调用方能区分结果与故障。

测试同时覆盖底层函数和实际的 `python -m offline_devkit` 子进程调用。权限错误采用模拟方式，因为 CI 或 root 用户可能绕过普通文件权限。

真实子进程测试还会检查 UTF-8 与 LF 输出，防止 Windows 自动把换行转换为 CRLF。深层 JSON 测试检查格式化的受控错误；不假定所有 Python 版本的解码器具有相同深度限制。
